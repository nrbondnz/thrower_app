Thrower App · Architecture Reference

App Architecture

A Flutter app for iOS and Android. A phone on a static mount, off to the side of the throwing lane, watches a 5-ring board (5 for the inner ring down to 1 for the outer) and scores each knife thrown at it. Everything runs on the phone; there is no backend yet. Click any solid box in the diagram for what that component is; click a card below it for the full flow it's part of.

Operational notes

Layer rules

  • lib/vision and lib/scoring have no Flutter imports: they run in background isolates and in tests on a PC.
  • Vision depends only on the camera layer's data type, CameraFrame, never on a plugin.
  • Plugins stay behind interfaces (TargetCamera, RecordingSound, SignalSounds), so tests feed recorded frames and fake sound.

Off the UI thread

  • Frame conversion, ring finding and the entry search run through compute, with top-level functions and plain data.
  • The motion pass stays on the UI thread: brightness only, at ~320 px.

On the phone only

  • Camera frames never leave the phone, and nor do the game history and the player names (files in the app's own folder). The only network calls are sign-in to the accounts backend (AWS Amplify, stage 2), and only when the build has its settings and the user signs in.
  • The camera records no sound today. Recording and sharing (backlog #11) would change that, and needs the Review Agent.
